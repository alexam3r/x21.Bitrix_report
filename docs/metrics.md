# Метрики отчёта по задачам Bitrix24

Источник правды для расчёта в `code/aggregate.js`. Любое изменение формул —
сначала здесь, потом в коде и тестах.

## Отчётный период

Период задаётся полуинтервалом `[start, end)` в ISO 8601:
- **Месяц:** `start` = 00:00 1-го числа месяца, `end` = 00:00 1-го числа следующего месяца.
- **Квартал:** аналогично по границам квартала.

Дата задачи «попадает в период», если `start ≤ дата < end`. Полуинтервал исключает
двойной учёт задач на стыке периодов.

## Роли сотрудника в задаче

Задача относится к сотруднику, если он:
- **Исполнитель** — `RESPONSIBLE_ID == userId`; **или**
- **Соисполнитель** — `userId ∈ ACCOMPLICES`.

Аудиторы (`AUDITORS`) и постановщик (`CREATED_BY`) в расчёт **не** входят.

Ведём два разреза по каждому счётчику:
- **как исполнитель** — основной, за него отвечает по премии;
- **участие (любая роль)** — исполнитель ИЛИ соисполнитель.

Если сотрудник одновременно исполнитель и соисполнитель одной задачи (редко) —
в «участии» задача считается **один раз** (дедуп по `ID` задачи в рамках сотрудника).

## Счётчики

Обозначения: `D = DEADLINE`, `C = CLOSED_DATE`, задача «закрыта» = имеет `CLOSED_DATE`
и финальный статус (см. «Статусы»).

| Счётчик | Условие | Смысл |
|---|---|---|
| **Выполнено за период** | задача закрыта И `C ∈ [start, end)` | Реальный объём сделанного — основной показатель премии |
| **К выполнению в периоде** | `D ∈ [start, end)` | Знаменатель — что ожидалось сдать в периоде |
| **Выполнено в срок** | из «к выполнению»: закрыта И `C ≤ D` | Качество/надёжность |
| **Просрочено (= не выполнено)** | из «к выполнению»: НЕ (закрыта И `C ≤ D`) | Красный флаг; см. ниже |
| **Без срока** | `D` отсутствует | Отдельная строка, в `%` не входит |

### % выполнения

```
% = Выполнено в срок / К выполнению в периоде        (если знаменатель > 0)
% = null                                             (если К выполнению = 0)
```

`null` рендерим как «—», чтобы не путать с 0%.

### «Просрочено = не выполнено» — точное правило

Задача из множества «к выполнению» (`D ∈ период`) считается **просроченной**, если
на момент расчёта выполняется любое из:
- не закрыта вовсе; **или**
- закрыта после дедлайна: `C > D`.

То есть «просрочено» = «к выполнению» − «выполнено в срок». Задача, закрытая позже
дедлайна, засчитывается в **выполнено за период** (по факту закрытия), но НЕ в
«выполнено в срок» и попадает в «просрочено».

## Статусы Bitrix24 (tasks.task.list, поле STATUS)

| Код | Значение |
|---|---|
| 1 | Новая |
| 2 | Ждёт исполнения |
| 3 | Выполняется |
| 4 | Ждёт контроля (условно завершена) |
| 5 | Завершена |
| 6 | Отложена |
| 7 | Отклонена / отменена |

Правила:
- **«Закрыта» для расчёта** = `STATUS == 5` (Завершена) И наличие `CLOSED_DATE`.
  Статус 4 (ждёт контроля) НЕ считаем закрытой — работа ещё может вернуться.
- **Отклонённые (7)** не считаются выполненными; если у них дедлайн в периоде —
  попадают в «просрочено» как невыполненные.
- Значение и набор статусов уточнить на реальном портале при интеграции
  (кастомные статусы/этапы возможны). Кодовое сопоставление вынесено в константу
  в `aggregate.js`, чтобы правку делать в одном месте.

## Метрики фазы 2

### Учтённое время (⏱)

Источник — `task.elapseditem.getlist` (записи учёта времени) за период по
`CREATED_DATE`. Секунды суммируются по **`USER_ID` записи** — т.е. время
принадлежит тому, кто его залогировал, независимо от того, кто исполнитель
задачи. Показывается в отчёте только если > 0. Требует включённого учёта
времени в задачах на портале — иначе будут нули (это не ошибка).

### Переносы дедлайнов

Источник — `tasks.task.history.list` с фильтром `{FIELD: 'DEADLINE'}` по каждой
задаче с дедлайном в периоде. **Переносом** считается запись истории, где
`value.from` и `value.to` оба непусты и различаются; первоначальная установка
срока (from пустой) переносом не считается. Переносы атрибуцируются
**исполнителю** задачи. Два числа: `deadlineShifts` (всего переносов) и
`tasksRescheduled` (задач хотя бы с одним переносом).

Стоимость: один запрос на задачу. Ограничение `maxHistoryTasks` (по умолчанию
300); если задач больше — остаток пропускается, и его количество возвращается в
выходе ноды как `historySkipped` (молчаливого обрезания нет).

## Фильтрация в отчёте

Сотрудники **без единой задачи за период** (по разрезу «участие»: `completed == 0`
и `due == 0`) в текст отчёта **не включаются** — это же автоматически убирает
технические аккаунты. Фильтр применяется на этапе формирования текста
(`report.js`), агрегация считает всех.

## Граничные случаи (проверяются тестами)

- Задача с `C` ровно на `end` периода → НЕ входит (полуинтервал).
- Задача с `C` ровно на `start` → входит.
- Задача без дедлайна, но закрытая в периоде → входит в «выполнено за период»,
  строка «без срока», в `%` не влияет.
- Задача с дедлайном в периоде, закрытая до дедлайна, но `C` уже в СЛЕДУЮЩЕМ
  периоде → в текущем «к выполнению»/«в срок» да; в «выполнено за период» — нет
  (это факт следующего периода). Разные даты — разные периоды, это by design.
- Пустой период (нет задач) → все счётчики 0, `%` = null, отчёт не падает.
- Один и тот же сотрудник исполнитель+соисполнитель в одной задаче → учёт один раз.
